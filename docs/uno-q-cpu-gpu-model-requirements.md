# UNO Q CPU/GPU向け座標推論モデル要件

更新日: 2026-09-11

## 目的

400 × 300 × 5 mmのアクリル板をKX134-1211で中央一点計測し、打撃位置を推定するモデルを、Arduino UNO QのCPU向けとGPU向けにそれぞれ最適化する。学習とモデル生成は、元の実測データが保存されている別の開発環境で行う。UNO Q実機はその環境に接続されていないため、実機への組込み、実行バックエンド確認、速度・負荷・カメラ併用試験は本リポジトリ側のセカンダリ環境で行う。

CPU版とGPU版は、単に同じモデルファイルの実行先を変えるだけでなく、各バックエンドに適した構造・量子化を選んでよい。ただし入出力契約、評価データ、座標系は共通にし、精度と実機性能を公平に比較できるようにする。

## 学習データの所在と受け渡し

- 本リポジトリには、元開発環境で収録したKX134の512点生波形セッション一式は含まれていない。
- `data/position_model_400x300/parity_cases.npz` は60件の照合用データであり、再学習用データセットではない。
- `uno_q_app/python/mpu9250_training_seed.npz` はKX134実測値から別センサ相当に変換した派生データであり、KX134ネイティブモデルの原本データにはしない。
- 別の開発環境では、元のKX134実測セッションを読み込み、データセットのファイル一覧、件数、SHA-256、収録条件を `dataset_manifest.json` に残す。
- 大容量の生データをGitへ追加するかは容量を確認して決める。追加しない場合でも、元データの絶対パスだけに依存せず、相対的なデータルートを指定できる学習コマンドとmanifestを成果物に含める。

## 共通データ契約

| 項目 | 要件 |
|---|---|
| センサ | KX134-1211、Z軸を基本入力とする |
| レンジ | ±32 g |
| サンプリング | 25,600 Hz |
| イベント長 | 512サンプル |
| プリトリガ | 64サンプル、trigger index 64 |
| 板 | 400 × 300 × 5 mm、4列 × 3行 |
| 教師位置 | 12エリア中心＋各エリア四隅付近の計60固定点 |
| 座標 | 左上原点、右方向をX、下方向をY、単位mm |
| 必須メタデータ | session ID、収録日時、打点ID、反復番号、座標、打撃者、センサ取付状態、取得設定 |

波形には、クリッピング、無打撃、二重打撃、取得欠落を識別できる品質情報を付ける。品質不良を無条件に削除せず、除外理由と件数をmanifestへ記録する。

## 分割と評価の原則

- 同一セッションのイベントをランダムに学習・評価へ分けない。
- 日、打撃者、センサ再取付けのいずれかが異なるセッションを評価側へ固定し、収録固有情報の暗記を避ける。
- CPU版とGPU版は完全に同じ学習・検証・テストIDを使用する。
- 最終的な比較用テストセットは学習処理から読み取り専用にし、そのイベントIDとハッシュを保存する。
- 60固定点のtop-1だけでなく、12エリア精度、XY距離誤差、確率校正、境界付近の誤りを評価する。
- 既存v7モデルを同じ固定テストセットで再評価し、CPU/GPU候補の基準値にする。データ分割が異なる過去指標を直接合否判定に使わない。

## 共通出力契約

各モデルは少なくとも次を生成できる構造にする。

1. 60固定点に対する正規化済み確率
2. 最大確率点の座標（MAP XY）
3. 60点確率の期待値による座標（expected XY）
4. 直接座標回帰値（direct XY。採用しない候補でも比較用に保持）
5. 12エリア番号と12エリア確率
6. 最大確率、90% credible set、X/Y分散または同等の不確かさ

モデル本体の出力を60確率と直接XYに限定し、12エリア集約や不確かさ計算を共通CPUコードで行ってもよい。CPU版とGPU版で後処理式を共通化すること。

## CPU最適化モデル

### 推奨構成

- 第一候補は現在の714特徴量（時間波形、FFT、統計量）を入力する小型MLPまたはその単一モデル化。
- TensorFlow LiteのCPU実行とXNNPACKで効率よく処理できる、固定shapeのDense、ReLU、Softmaxなど標準演算を優先する。
- FP32を精度基準とし、FP16重み、動的範囲量子化、INT8全量子化を比較する。INT8では代表データを全60点・複数セッションから均等に選ぶ。
- アンサンブルが精度に必要な場合も、6個の独立interpreterではなく、一つのグラフまたは一括行列として実行できる形式を優先する。
- 特徴抽出はCPU上で行い、学習時と実機で窓関数、FFTスケール、正規化を一致させる。

### CPU版の成果物

- `acrylic_pan_xy_cpu_fp32.tflite`
- 採用する場合は `acrylic_pan_xy_cpu_int8.tflite`
- `cpu_model_metadata.json`
- PC上でTFLite出力と学習フレームワーク出力を比較するテスト

## GPU最適化モデル

### 推奨構成

- Adreno 702のOpenCL対応GPU delegateで全層または大部分を委譲できる固定shapeモデルにする。
- GPU版はモデル表現力を増やす目的を持たせ、512点波形を入力する1D CNNを第一候補とする。実装上はGPU delegateが扱いやすい2D Convへ変換してもよい。
- Conv、Depthwise Conv、Dense、ReLU、Pooling、Addなど、使用するGPU delegateで対応確認できる演算を優先する。
- 動的shape、制御フロー、モデル内FFT、細かい非対応演算を避け、CPU/GPU間の分割実行とテンソル往復を最小化する。
- FP16重みを第一候補とし、FP32基準モデルとの座標誤差・確率差を検証する。
- interpreterとGPU delegateは起動時に一度生成してウォームアップし、打撃ごとに再生成しない。可能ならOpenCLカーネルキャッシュを利用する。
- カメラ処理もGPUを使用する可能性があるため、振動推論単独だけでなくUSBカメラ表示・推論との同時負荷を測定する。

### GPU版の成果物

- `acrylic_pan_xy_gpu_fp16.tflite`
- 比較用の `acrylic_pan_xy_gpu_fp32.tflite`（実用上不要なら生成スクリプトで再現可能でもよい）
- `gpu_model_metadata.json`
- GPU delegate互換演算一覧と、想定される委譲率
- PC上でTFLite出力と学習フレームワーク出力を比較するテスト

## DSPの扱い

QRB2210にはHexagon DSPがあるが、現在のUNO Q Debian環境ではQNN/SNPE、FastRPC、対応デバイスノードを確認できていない。また、現在のリアルタイム取得と衝撃検出はSTM32U585が担当しているため、DSPへ移す実益は小さい。

DSPモデルは今回の必須成果物にしない。将来、常時監視時の消費電力低減、音声処理、センサ融合、FFT前処理のオフロードが必要になり、QRB2210対応の正式なSDK・配布可能なランタイムが確認できた場合に別タスクとして評価する。DSPをNPUまたはHTPとして扱えるとは仮定しない。

## 精度の候補選定条件

同じ固定テストセット上で次を確認する。

- 既存v7に対し、60点top-1、12エリア精度、平均・中央値・p90/p95距離を悪化させない。
- 量子化／FP16化による12エリア精度低下は0.5ポイント以内を目安とする。
- 量子化／FP16化による平均XY距離の増加は10%以内を目安とする。
- 確率をUIへ表示するため、NLL、Brier score、ECEも比較し、必要なら温度校正を行う。
- CPU版とGPU版の構造が異なる場合、速度だけでなく別日・別打撃者・再取付けセッションでの頑健性を優先して最終採用する。

## このUNO Qで行う受入試験

別開発環境ではUNO Q実機性能を推測して合否を決めない。成果物受領後、本セカンダリ環境で以下を行う。

1. CPU interpreterとGPU delegateのロード可否を確認する。
2. 実行ログまたはdelegate情報から、GPU版が実際にGPUへ委譲されたことを確認する。GPU要求時にCPUへ黙ってfallbackした結果をGPU測定値として扱わない。
3. `parity_cases.npz` 全件について、PC基準出力との最大差、座標差、クラス一致を確認する。
4. 初回とウォームアップ後を分け、前処理込み推論時間のp50、p95、最大値を測る。
5. CPU使用率、メモリ、温度、連打時の欠落、80 ms再トリガー内での完了率を測る。
6. USBカメラ停止時と動作時の両方で測り、カメラFPS、Web UI応答、振動推論遅延への干渉を確認する。
7. 実センサ打撃で、取得からUI・発音までのend-to-end遅延と推論安定性を確認する。

目標は、ウォームアップ後の前処理込みp95を80 ms未満とすること。演奏応答の余裕を確保するため20 msを望ましい目標とし、GPU版はCPU版よりモデル精度、p95遅延、CPU解放効果のいずれかで明確な利点がある場合に採用する。

## 現時点の基準値

- 現在配備中のNumPy CPU版は約8.9 MB、概算約220万MAC/イベント。
- UNO Q上のparity self-testは、ウォームアップ後おおむね22～24 ms、初回約45 ms。
- 現在の再トリガーガードは80 ms。
- 現在の環境はAdreno 702をMesa OpenCLから認識するが、TensorFlow Lite GPU delegateの実装と配備は未完了。

CPU版はまず現在の精度を小さな計算量で再現する役割、GPU版は将来の表現力拡張とカメラ併用時のCPU余力を評価する役割とする。どちらかを事前に固定採用せず、上記の実機受入試験で決定する。
