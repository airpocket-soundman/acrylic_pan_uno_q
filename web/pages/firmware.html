06 / UNO Q software architecture

リアルタイム収録とAIを、
2つの計算系に分ける。

STM32U585はKX134の決定論的な取得とイベント化、QRB2210/Linuxは保存、前処理、推論、Web UI、発音を担当します。モデル更新がセンサ取得の安定性へ影響しない境界を作ります。

STM32U585

Real-time capture

SPI、3軸リングバッファ、割込み、timestamp、打撃候補切出し、品質flagを担当します。

QRB2210 / LINUX

AI application

session保存、前処理、ONNX等の推論、confidence判定、ヒートマップ、発音、診断ログを担当します。

データフロー

SENSOR

KX134 × 3 axes

SPIで連続取得し、立上り前を含む波形を保持。

→ Bridge
EVENT

Versioned message

sequence、timestamp、条件、品質flag、波形を転送。

→
INFERENCE

Linux runtime

領域、XY、強度、confidenceを出力。

責務と合格条件

GPIO / SPISTM32コネクタ導通と電圧確認後、WHO_AM_I読出し成功
イベント取得STM32100イベントでsequence欠落・overrun・破損が0
永続化Linuxsession manifestとNPZの件数・hashが一致
前処理Linux学習と実機のgolden vectorが許容誤差内
AI推論Linux固定hold-out精度と実機p95 latencyを記録
障害時両方sensor、Bridge、model errorを区別して記録

互換資産の扱い

COBS + CRC32、sequence、session形式、旧ダミーモデルのgolden caseは再利用候補です。旧ML63Q2557向けJ-Link、UARTF1、Solist-AI 128-64-8 runtimeは firmware/ に比較資料として保持しますが、UNO Qの現行runtime要件にはしません。

配線確定前の注意独自コネクタのピンを名称だけで推測してUNO Qへ接続しません。GND、電源、SPI各線、割込みを回路資料と導通測定で確定し、配線versionとして記録します。

開発順

01

SPI疎通

安全な電圧でKX134のIDとレジスタread/writeを確認します。

02

連続収録

3軸リングバッファ、trigger、Bridge、session保存をend-to-endで検証します。

03

dataset作成

実機収録と品質検査を行い、session単位のsplitを発行します。

04

モデル統合

baselineから深層モデルへ段階的に置換し、精度と実機latencyを比較します。

現行アプリは uno_q_app/、旧ML63Q2557資料は firmware/ に分離しています。全体の優先順位は 実装計画 を参照してください。
